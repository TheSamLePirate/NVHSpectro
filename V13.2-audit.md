# NVH Spectro V13.2 — Full Code, Architecture & Metrology Audit (current version)

**Scope:** The application **as it exists today** — branch `aaa/phase0`, commit `157cd3d` (Phase 4 + GPS-4 complete). App module, `:core` module, build system, CI, tests, docs. The `v2/` scratch directory and untracked working files are noted only where they matter.
**Date:** 2026-08-27
**Benchmark:** A *real* AAA bar — a field instrument an acoustic engineer can defend in front of a customer: metrologically validated, correct under concurrency, tested at every layer, releasable, and honest about what it cannot prove.
**Method:** Full manual read of all 75 production Kotlin files (~15,500 lines), build files, CI workflow and hygiene gates, manifest, resources, test suite (202 tests), and cross-check of every claim in `AAA-TRACKING.md` against the actual tree. Findings cite `file:line` of the current tree.

## 1. Executive Summary

The V13.1 audit called this codebase a C− prototype. That audit was correct, and the remediation campaign that followed (Phases 0–4, GPS-0–GPS-4) was executed with a rigor most professional teams never reach: a 2,024-line god ViewModel is gone, the sample-rate corruption is fixed and CI-gated, the GPS chain is a genuinely defensible Kalman design with an error budget propagated into the order search, and the app is honest about what its metrics are not. **The measurement-correctness class of defects that defined V13.1 (wrong sample rates, misparsed WAVs, leaked consumers, crashed pipelines) is, as far as this audit can establish, closed.**

But this audit is written against a real AAA bar, not against last year's code. Judged that way, the current version is a **well-engineered B/B− software project wrapped around a metrology chain that has never once been validated against ground truth.** The gap to AAA is no longer code quality — it is **evidence**:

1. **Every number the app displays is unvalidated on hardware.** All estimator constants, detector gates, and validity thresholds are labeled `PROVISIONAL` in-code — correct, honest — and the field campaign that would freeze them (GPS-5: 3 phones vs ground truth, bias/MAE/RMSE/P95, σ-coverage, full-tracking A/B) **has not run**. Every device gate in `AAA-TRACKING.md` was executed on one emulator model (API 37). No physical phone has ever been shown in evidence.
2. **A real regression sits in the analyzer hot path:** the full-file order sweep (~10⁷–10⁸ operations on a 5-minute file) runs **synchronously on the main thread** — after every load and on every kinematics/tracked-order change. V13.1's C6 freeze was fixed for capture and export, then quietly reintroduced for the WAV sweep when the computation was extracted but the call sites were not dispatched.
3. **The release story does not exist yet:** no signing config (debug-keystore ad-hoc signing), `applicationId` still `com.example.nvhspectro`, no version tags, no changelog, zero instrumented/UI tests (the `androidTest` dependency set is declared and sources the empty set), no macrobenchmark, and the master branch does not contain the work.
4. **The last mile of the V13.1 findings lives in the display/export seam:** per-frame O(history) list copies at 43 Hz, four `DoubleArray(1024)` allocations per frame in the TTNR path, ~1,250-line `AppScreen` composable collecting ~35 flows at the top, French text and hex colors hard-coded in the export layer where the new CI gates cannot see them.

**Overall grade: B− software engineering, C instrument-readiness, against the AAA bar.** The architecture now deserves its DSP. The instrument does not yet deserve a customer signature, and the project knows it — the code says `PROVISIONAL` in a dozen places. What separates this version from AAA is not another refactor; it is a field campaign, a release pipeline, and a UI test layer.

## 2. The gap that outranks all code findings: no field validation exists

This is not a finding against the code — the code *documents* its own provisional status (`OrderSearchPolicy` header, `GnssSpeedSession.Config`, every `PROVISIONAL` constant). It is a finding against the program. For an instrument whose purpose is producing customer-deliverable reports:

- **The Kalman gains, validity thresholds (2 s horizon, 350 ms freshness, σ>3/1.5 m/s gates), NIS gate χ²(1)=9, stationary hysteresis — all were picked from simulated σ-growth profiles on one chipset, an emulator's** (`AAA-TRACKING.md` GPS-2). No `doc/VALIDATION.md` exists; GPS-5 has not started.
- **V1000's own uncertainty is explicitly not modeled** (`OrderSearchPolicy.kt:14`): dynamic tire radius, load deflection (a flat 1.5 %), gear-ratio rounding. For H18 at V1000 = 10 km/h, a 1.5 % radius error alone moves the projection ~7.6 Hz — comparable to the entire GNSS σ term the new windows were built around. The error budget is rigorous about the term that is easy to measure and silent about the term the user types.
- **The emergence index (ex-TTNR) remains an uncalibrated heuristic.** The renaming to "Indice d'émergence NVH" with a "not ECMA-74" footnote on the PDF (plan 4.5) resolves the *liability*, not the *science*: the tone side sums ±2 bins of coherently-calibrated leakage against a noise side computed as a PSD with **no ENBW correction** (`FFTProcessor.kt:146`) — a fixed ~1.8 dB bias baked into every displayed and reported emergence value, acknowledged in the `DisplayMode.TTNR` doc but never corrected or characterized. Around it: 43/45 Hz gates, −75/−85 dBFS frequency-profiled gates, Terhardt bandwidth clamped [150, 350] Hz, a synthetic "dome" at peak−4 dB, a −1.5 dB offset — **eleven magic constants, zero of them validated against any reference signal suite** (the golden snapshot pins behavior, not correctness).
- **All device evidence is one emulator.** DEV-7, DEV-11, DEV-12, DEV-13, DEV-20, DEV-31, DEV-38, DEV-45, DEV-52 — nine open hardware follow-ups, including the Android-10 save path (DEV-11), the mic-busy path (DEV-13), and the estimator drive tuning (DEV-20). `audit-gps.md`'s own verdict — "ne doit pas encore être présentée comme une mesure de vitesse qualifiée" — is still the accurate one.

**What AAA looks like here:** a frozen-parameter release candidate validated on ≥3 physical devices against a reference (even a phone strapped next to a calibrated tachometer/DAQ), a `VALIDATION.md` with bias/RMSE/P95 and σ-coverage per device, and constants moved from `PROVISIONAL` to versioned config. Nothing in the remaining work is harder than what was already done in Phases 0–4; it simply hasn't been done.

## 3. Critical Findings

### C-1. Full-file order sweep runs on the main thread — the C6 freeze, reintroduced by extraction — **Critical**

`AnalyzerViewModel.recalculateOrderTrackingForWav()` (`AnalyzerViewModel.kt:336`) executes `WavAnalysis.orderSweep()` synchronously on whatever thread calls it. Two call sites:

1. `processFullWavSpectrogram()` — inside `withContext(Dispatchers.Main)` (`AnalyzerViewModel.kt:280`), i.e. **after every WAV/video load**, the sweep runs on main.
2. `updateKinematicsConfig()` / `updateSelectedTrackedOrder()` → `rerunWavTrackingIfLoaded()` (`AnalyzerViewModel.kt:92–105`) — called from dialogs, i.e. **on the main thread, inline**.

The cost is not small. `orderSweep` (`WavAnalysis.kt:227–303`) is O(frames × (1024-bin readout + per-frame `OrderTrackingEngine.step`: 1024-bin fold into a 1000-order grid + 1000-bin EMA + 1000-bin local-max/tag scan + report merge)). For the flagship 5-minute case (~12,900 frames) that is on the order of 5×10⁷ float operations plus per-frame `FloatArray(1000)` allocations and a 12,900-entry `tagsByFrame` map — **hundreds of ms to seconds of frozen UI**, every time the user nudges V1000, changes gear mode, or selects a different tracked order. `WavAnalysis` was extracted to `:core` precisely to be testable and dispatchable (plan 3.3); the testability arrived, the dispatch did not.

**Impact:** with kinematics enabled on a long file, every kinematics edit freezes the UI with no progress state — exactly the behavior the V13.1 audit flagged at `MainViewModel.kt:445–631`, rebuilt one layer lower. A user tuning the vehicle model mid-analysis will perceive the app as hung.

**Fix:** `recalculateOrderTrackingForWav` belongs in a `Dispatchers.Default` job (it already has a cancellation sibling in `processingJob`), with the 2048-line `tagsByFrame` map kept off the session until done, and a "recalcul…" state on the progress overlay. Also hoist `OrderTrackingEngine.step`'s per-frame `FloatArray(ORDER_BINS)` and fold with rounding, not truncation (`OrderTrackingEngine.kt:57` — `toInt()` biases every order down by up to 0.05 order, silently interacting with the 0.25 whitelist tolerance).

## 4. High Findings

### H-1. Saving a recording is broken on every supported Android below 10 — **High**

`AndroidManifest.xml:5` declares `WRITE_EXTERNAL_STORAGE` with `maxSdkVersion=29`, but `Permissions.kt` requests only RECORD_AUDIO + locations (`Permissions.kt:80–82`); the storage permission is **never requested at runtime**. On API 24–28 (minSdk is 24), `RecordingStore.saveViaLegacyFiles()` (`RecordingStore.kt:136–146`) writes to the public Downloads directory, which requires that runtime grant → `mkdirs()` fails → `IOException("Dossier inaccessible… permission stockage requise")` → the user's 30-second field measurement survives in RAM only, with an error banner whose remedy (grant a permission the app never asks for) is unreachable without going to system settings blind. The failure *surfaces* (the V13.1 silent-loss defect is fixed) but the feature is dead on 5 API levels the app claims to support. Either request the permission on ≤28, or use `getExternalFilesDir` (app-private, no permission) for the legacy branch — the latter is the correct choice for a measurement tool.

### H-2. `MeasurementSession` mutates shared state from two threads with no synchronization — **High**

The engine classes are `@Synchronized` "as a belt on top of single-thread confinement" — but the session itself is not. `appendLiveFrame`/`appendLiveTelemetry` run read-modify-write cycles on `MutableStateFlow` values from the `nvh-dsp` thread (`session.fftHistoryAbsolute.value.toMutableList() … .value = …`), while the main thread simultaneously runs `resetAnalysisState()` + `clearStreams()` through the mode-transition hooks (`MeasurementSession.kt:75–79`). StateFlow *assignments* are atomic, but the copy-add-trim cycle is not: a `clearStreams()` landing between an append's read and write **resurrects stale rows** into the freshly cleared history, and a frame processed by the DSP thread after the wipe but before `captureEngine.setEnabled(false)` takes effect appends post-reset engine output onto an empty history. The window is milliseconds and the consequences are cosmetic today (one ghost column) — but the design documents confinement as the safety model while violating it at the session boundary. Either confine all session mutations to the DSP thread (main asks via a command flow), or synchronize the session methods like the engines.

### H-3. Live path still allocates ~10 MB/s of garbage at 43 Hz — **High** (perf, V13.1 P2 residue)

Per frame, the live pipeline allocates: two full history-list copies + one telemetry-list copy with `removeAt(0)` shifting every element (`MeasurementSession.kt:157–178`, `:216–223` — for a 5 s window at 2048/44.1 kHz that is ~1,300-element `ArrayList` copies ×3); inside `FFTProcessor.computeTTNR`, four fresh `DoubleArray(1024)` (`powerLinear`, `rawTtnr`, `filteredTtnr`, `finalTtnr`); in `LiveAnalysisEngine.processFrame`, a `validated` + `smoothed` pair (8 KB) plus `rawTtnr.clone()` into the retro ring; in `OrderTrackingEngine.step`, a `FloatArray(1000)` frame spectrum. `processFFT` itself is clean (preallocated, plan 3.7) — everything downstream of it was not converted. Roughly 200+ KB of short-lived objects per frame at 43 fps. No benchmark exists to say whether this matters on a mid-range device — which is the deeper finding (see §9): the perf work was justified by static reasoning in both audits and never *measured*.

### H-4. `AppScreen` is still a ~1,250-line composable reading ~35 flows at the top — **High** (V13.1 A5/P3 residue, partially addressed)

`MainScreen.kt:96–1348`: one composable collects 35+ `StateFlow`s (43 Hz telemetry among them) and renders the scaffold, both panes, the KPI strip, four overlay systems and every dialog. `collectAsStateWithLifecycle` fixed the background cost (P4); the **structural** problem — any of those 43 Hz emissions recomposing the whole tree including the bottom bar and dialogs — is untouched. `SpectrogramColormap.kt` (1,206 lines) remains the second monolith, with 60+ `remember(dimens) { Paint().apply { … } }` declarations and a draw routine handling spectrogram, axes, cursor, beacons, H1 overlay and tags in one scope. The decomposition discipline that was applied to the ViewModels (2,004 lines → three VMs ≤ 296 lines + `:core`) was never applied to the UI. This is where the next audit's regressions will come from.

### H-5. Zero instrumented tests; the UI layer is entirely unverified by automation — **High**

`app/src/androidTest/` does not exist — yet `build.gradle.kts` declares the full instrumented stack (`ui.test.junit4`, espresso, test runner). 202 tests, 158 of them in `:core` at ≥90 % line coverage, is a genuine achievement for this codebase's history, but the coverage gate covers **only `:core`**; the app module (UI, ViewModels' Android halves, permission gating, `RecordingStore`, `PlaybackController`) is unit-covered by exactly 6 thin classes. There are no Compose UI tests of the permission matrix that Gate 4 verified *by hand on an emulator*, no screenshot tests for the plot geometry work (plan 4.2's zoom-alignment is exactly the kind of invariant that silently regresses), no Paparazzi/Robolectric rendering test of the spectrogram, and no `ReleaseAlarm`-style end-to-end. An AAA app's *riskiest* code — the capture/presentation seam — is its least-tested.

## 5. GNSS / Speed Chain (current state)

The V13.1 §3b defects are closed in substance: monotonic clocks everywhere, GPS_PROVIDER-only metrology with typed provenance, speed-accuracy-keyed LED, hardware audio-timestamp anchoring (`AudioRepository.kt:165–192`), Kalman with real covariance and NIS-gated outlier rejection, validity propagation into σ-driven, identifiability-bounded order windows (`OrderSearchPolicy.kt`), and RTS reconstruction on reload. This is now the strongest subsystem. Residuals:

- **G-a (Medium). All thresholds provisional and single-chipset.** See §2. The A/B α-β baseline exists but the full-tracking switch is a constructor flag with no UI (`SpeedProvider.kt:63`), and the tuning data it needs comes only from the debug-only `FieldLocationLogger` — the release build collects nothing, so the GPS-5 campaign must be an explicitly instrumented one.
- **G-b (Medium). `TelemetryData` still carries 0-as-unknown sentinels.** `SpeedProvider.buildTelemetry()` (`SpeedProvider.kt:298–313`): `latitude/longitude/altitude ?: 0.0`, `speedAccuracyMs ?: 0f`, `elapsedRealtimeNanos ?: 0L`. GPS-0.4's rule — "no numeric sentinels in contracts" — was applied to `GnssSpeedSample`/`SpeedEstimate` but not to the display-side `TelemetryData`, and the v3 sidecar therefore encodes `altitude: 0.0`, `speedAccuracyMs: 0.0` for unknowns (`TelemetryCodec.kt:44–46`), which a downstream consumer (or another tool) can only interpret as "at sea level with perfect σ". The σ path was fixed (nullable); the position/altitude path was not.
- **G-c (Low). Raw `fix.speed` displayed as "GPS speed" next to the Kalman "Théo" speed** (`SpeedProvider.kt:300`) — two speeds on screen whose difference the operator may read as an error indicator, when it is measurement vs estimate. A tooltip/label stating which is which exists in docs, not in UI copy.
- **G-d (Low). `qualityOf` staleness uses `lastFixElapsedNanos = Long.MIN_VALUE` sentinel** (`SpeedProvider.kt:82`) — correct but fragile arithmetic on a sentinel; `now − MIN_VALUE` overflows to a large positive, which happens to work. Type it (`Long?`) like the σ was typed.

## 6. DSP & Measurement Integrity (current state)

- **D-a (Medium). Emergence index: uncalibrated, magic-constant detector** — fully detailed in §2; the honest naming mitigates the reporting risk, not the measurement one. An AAA instrument either implements the named standard or publishes a calibration note for the index (reference-tone suite, bias vs SNR, detection thresholds). Neither exists.
- **D-b (Medium). `computeTTNR` state and the transient gate interact subtly.** The shock detector *skips the entire TTNR pass* on a shock frame (`FFTProcessor.kt:87`) — including the linear-power EMA update, which is correct (hold) — but `integratedTtnrPower` is also skipped for the *retro-unmask* raw rows that `LiveAnalysisEngine` collects, so retro rows are raw while their neighbors are integrated, by design, again (the V13.1 D2 scale-mixing concern, now on the new [0,30] scale — visible as a brief brightness jump at retro-unmask). Cosmetic, undocumented in the user docs.
- **D-c (Low). FFTProcessor window is symmetric Hann (`fftSize−1` denominator) used with 50 % overlap** — the periodic form is the standard for STFT; the symmetric choice produces a slightly different COLA behavior. Harmless at these sizes; worth one line of rationale.
- **D-d (Low). Live capture is hard-locked to 44.1 kHz** (`AudioConfig.LIVE_SAMPLE_RATE_HZ`) while the C1 fix correctly threads file rates. Some devices resample 44.1 → 48 kHz internally with quality cost; the pro choice is to open the device's native rate and carry it like a file's. Currently the app is self-consistent (provenance records the route), so this is an optimization, not a defect.
- **D-e (Low). Jet colormap is still the only palette** (V13.1 D8, never addressed). Perceptually non-uniform, false luminance edges; the export hard-codes the same. At least offer Viridis/Turbo for quantitative reading.

## 7. Architecture (current state)

- **A-a (Medium). `MeasurementSession` is a 372-line grab-bag drifting back toward a god object** — mode, histories, telemetry, tags, report, kinematics, provenance, settings, notices, detector settings. It is *documented* and *test-covered* (`MeasurementSessionTest`), which the old MainViewModel never was, but it now has 20+ mutable flows and a documented escape hatch (`forceMode`, `MeasurementSession.kt:97–101`) whose contract is "never use for user-driven switches" — a comment-enforced invariant in a codebase that just proved it can arm CI gates for invariants. Gate it or split it.
- **A-b (Medium). Process-scoped session holds full spectrograms for the process lifetime** (DEV-25's deliberate direction): after the activity is finished, `session.fftHistory*` (up to ~26 MB FloatArray data for a 5-min file) lives until process death. Fine for a single-activity instrument; a memory leak by any other name if a future task stack appears. Trim on `isFrozen`/mode transitions or document the owner.
- **A-c (Low). Emergence report entries accumulate for the whole live session** (merged but never bounded) — a 1-hour drive with a drifting fundamental (tunnel, idle) can produce hundreds of merged rows rendered in the dialog. Bound or trim by age.
- **A-d (Low). `AudioRepository.estimatedClockLogged` is per-repository, not per-capture** (`AudioRepository.kt:216`) — a restart within the same ViewModel lifetime never re-logs the degraded-clock condition. Trivial.
- **A-e (Low). `PlaybackController.prepare` swallows all exceptions to `null`** (`PlaybackController.kt:96–100`) — a codec failure degrades silently to "duration = analyzed PCM duration"; only the WAV path notices via banner. Route prepare failures to the notice channel like capture errors.

## 8. Compose / UI (current state)

- **U-a (Medium). Tag fade reads `System.currentTimeMillis()` inside the draw scope** (`SpectrogramColormap.kt:1094`) — the alpha is correct only when something else triggers a redraw; in frozen mode or a stalled stream, tags freeze mid-fade at full opacity indefinitely. This is U2's pattern (side-effecting time in rendering), survived the refactor. Drive the fade from a frame clock (`withFrameNanos`) or bake expiry into state.
- **U-b (Medium). Export layers escape every new CI gate.** `PngExporter.kt:145–146,231–233` hard-codes French labels ("Pédale:", "Accél:") and hex colors (`#00E676`, `#FF9100`); `PdfReportGenerator.kt:143` (`#0055A4`); `ReportStamp.kt` hard-codes French sentences. The Compose-text gate and the colour-literal gate — both excellent — inspect **only Compose `Color(0x…)` and Compose text**. The customer-facing deliverables (PDF/PNG) are therefore un-gated for i18n and for the screen↔export palette consistency that plan 4.3 claimed (`NvhOrderTrace` ARGB sharing covers orders; the telemetry-graph colors diverge). Extend both gates to the `export/` package.
- **U-c (Low). `android:configChanges` includes orientation** (`AndroidManifest.xml:31`) — the activity never recreates on rotation, which conveniently means the app never exercises its own state-restoration path on rotation. With process death covered by DataStore this is defensible, but note that *activity* recreation (system-initiated) remains an untested path.
- **U-d (Low). Zoom state survives mode changes only by leave-report-mode reset** (`SpectrogramColormap.kt:164–169`); the pan/zoom pair is remembered per composition — re-entering report mode re-clamps, verified by plan 4.2's transform unification. No finding beyond "no UI test pins it" (see H-5).
- **U-e (Low). "Ordre ${count + 1}" default order name hard-coded in the ViewModel** (`ReportViewModel.kt:152`) — user-facing French outside `strings.xml`, invisible to the Compose-text gate (same class of miss as U-b).

## 9. Performance (current state)

- **P-a (High, = H-3).** Live-path garbage churn: see H-3. Ring buffers (`MeasurementSession`), preallocated TTNR scratch (`FFTProcessor`), and a fold that reuses the engine's spectrum buffer would take the live path to near-zero steady-state allocation.
- **P-b (Medium). No numbers anywhere.** The plan's own budget — "5-min WAV load < 3 s", "TOTAL PSS < 256 MB" — was verified once on an emulator (Gate 3) whose FFT throughput is flagged *in the same log* as unrepresentative. No Macrobenchmark module, no startup/baseline-profile work (a 43 Hz pipeline app is a textbook baseline-profile candidate), no frame-timing metric. AAA requires measured, budgeted performance on target hardware; this project has *asserted* performance twice and *measured* it never.
- **P-c (Low). `Spectrogram.dfHzAt` recomputes `nyquist/row.size` per call** in per-bin loops (cursor readout); trivial but free to hoist.

## 10. Build, Release & Process (current state)

- **R-a (High). The release artifact is unsigned and unidentifiable.** No `signingConfigs` block exists; Gate 0's APK was signed ad hoc with the debug keystore (DEV-8, plan step 5.5 still open). `applicationId` remains `com.example.nvhspectro` (decision D9 open). No version tags, no `CHANGELOG.md`, and the entire AAA campaign lives on `aaa/phase0` while `master` — the branch the remote HEAD points to — predates it. Until D9 + signing + a tag exist, there is nothing distributable that a customer could install, update, or attribute. For an app that produces signed-customer deliverables, its *own* artifact chain is the least trustworthy in the repo.
- **R-b (Medium). 497 ktlint + 500 detekt findings baselined** — the pre-existing style debt was frozen rather than paid (a deliberate, documented DEV-4/DEV-46 trade). The baselines mean `LongMethod`, `LargeClass`, `ComplexCondition` etc. on the *old* code can never fail CI, and the two UI monoliths (H-4) are structurally protected by the baseline. Pay down or delete per-rule; a baseline that includes `LargeClass` for files you plan to keep is a decision to keep them.
- **R-c (Medium). CI runs one JVM matrix, one emulator, once.** No device matrix (Firebase Test Lab / Gradle Managed Devices), no instrumented job (nothing to run — H-5), no minSdk-24/28/31 API-level matrix for the paths this audit flags (H-1, G-b, DEV-11), no release-build test variant. The hygiene-gate concept (`ci/checks.sh`, nine armed gates) is genuinely strong and should be the template for the next tier — which is device coverage.
- **R-d (Low). README badge says "Android 8.0+" while `minSdk = 24`** — either the badge is wrong or the manifest is. Also `allowBackup = true` with the template TODO rules untouched (`backup_rules.xml`, `data_extraction_rules.xml` — V13.1 S4, still open): DataStore settings and cache files get backed up by default; review or exclude.
- **R-e (Low). Working tree hygiene:** modified-but-uncommitted `README.md`/`doc/`/`AGENTS.md`/`.gitignore` at audit time; untracked `v2/` scratch project and `W2628_EOL_Result.pptx` still on disk pending clearance (carried from Phase 0). Trivial, but the tracking document's authority depends on the tree matching its claims.

## 11. Testing (current state)

- **T-a (Medium). Coverage asymmetry:** `:core` ≥ 90 % line-gated; the app module unmeasured, with 6 test classes for ~9,000 lines of Android-side code. `LiveViewModel`'s recording buffer choreography, `AnalyzerViewModel`'s load-generation guards, `SpeedProvider`'s provider fallback logic and `RecordingStore`'s dual paths are the highest-consequence Android code in the repo and are covered only by emulator smoke checks.
- **T-b (Medium). Golden tests pin behavior, not correctness.** The FFT golden snapshot (seed 42, tol 1e-9) protects against regressions — the right tool — but nothing validates *absolute accuracy* against synthetic references beyond the analytic single-tone cases (which are good: 0/−20/−60 dBFS, scalloping, Butterworth −3.01 dB points). An AAA DSP suite adds multi-tone + noise-floor reference spectra with published expected emergence values — the test would fail today, which is precisely the point (§2, D-a).
- **T-c (Low).** Test names reference finding IDs (`c1_*`, `gps2_*`) — excellent traceability; keep the convention now that IDs cross audits.

## 12. Documentation (current state)

## 13. What is genuinely AAA-grade already

Credit where due — these meet or exceed the bar and should not be regressed by the next campaign:

- **The GPS chain design** (§5): qualification → covariance-aware estimation → validity contract → σ-propagated, identifiability-bounded order windows → versioned, replayable field traces. This is defensible metrology engineering.

- **The honest renamings** (émergence NVH ≠ TTNR; "--" vs 0.0 km/h; truncation banners; UNPROCESSED vs VOICE_RECOGNITION in metadata): the app's epistemic hygiene is now better than its validation status.
- **The documentation discipline** (§12) and the deviation log culture (DEV-1…DEV-52) — a real engineering process, visible in artifacts.
