# NVH Spectro V13.1 — Full Code, Architecture & Correctness Audit

**Scope:** Legacy application at repository root (`app/`), build system, resources, tests, and repository hygiene. The `v2/` rewrite is explicitly out of scope.
**Date:** 2026-08-26
**Benchmark:** "AAA" quality bar — production-grade correctness, measurement integrity, architecture, concurrency safety, performance, and engineering process.
**Method:** Full manual read of all 39 Kotlin source files (~9,600 lines), manifest, Gradle configuration, ProGuard rules, resources, tests, and git-tracked repository contents.

---

## 1. Executive Summary

NVH Spectro is a genuinely useful field tool with real domain intelligence: the kinematics model (V1000 / gear-chain / tire geometry) is sound, the FFT amplitude calibration is correct in intent, and the order-tracking concepts (order-domain EMA, whitelisting, sub-bin parabolic interpolation) show strong NVH insight.

**It is not an AAA application. Measured against that bar, it currently sits at prototype/R&D grade.** The gap is not cosmetic — it is structural:

1. **Measurement integrity is compromised** in several paths: the analysis pipeline hard-codes 44.1 kHz in at least 9 places, so any imported WAV/video at 48 kHz (the most common video sample rate) produces silently wrong frequencies, wrong order tracking, and wrong report values. Stereo and non-canonical WAV files are misparsed. The microphone is captured through the processed `MIC` source (AGC/noise suppression active on most devices), which undermines dBFS stability for a measurement app.
2. **Concurrency and lifecycle are unsound**: every audio-settings change permanently leaks a competing channel consumer; all live DSP runs on the main thread; heavy sweeps and exports run on the UI thread; the microphone stays hot for the entire app lifetime regardless of mode; `MediaPlayer` is never released on ViewModel death.
3. **Effective test coverage is zero.** The only two test files in the project test dead Android Studio template code ("Hello Sample1!"), not one line of the actual application.
4. **The codebase carries heavy process debt**: a 2,004-line god ViewModel, ~130-line copy-pasted DSP blocks, dead features (an unreachable Emergence Report dialog), abandoned wrong code left in production (`BiQuadFilter.process()` with "Wait, is this Direct Form II?" comments), 89 one-off patch scripts, six APK binaries and compiler error logs committed to git, and a three-way version mismatch (git says V13.1, Gradle says 12.1.4, the About dialog hard-codes "v13.1").

**Overall grade: C− against the AAA bar.** The DSP ideas deserve better engineering than they currently receive. A prioritized remediation roadmap is in §14.

## 2. Critical Findings (correctness — wrong results or data loss)

### C1. Hard-coded 44.1 kHz corrupts all analysis of 48 kHz (and any non-44.1k) sources — **Critical**
The WAV reader and video extractor correctly capture the real sample rate (`WavDataReader.kt:60`, `VideoAudioExtractor.kt:40`), and `LoadedWavData.sampleRate` carries it. But the pipeline then ignores it in most places:

- `FFTProcessor.kt:39` — `df = 44100.0 / fftSize` inside `processFFT` (used for the 30 Hz cutoff), regardless of source.
- `MainViewModel.kt:507` — `val nyquist = 44100 / 2.0` in `recalculateOrderTrackingForWav`, **even though the correct `sampleRate` is read six lines up at line 450 and used at line 467**. The same function uses both.
- `MainViewModel.kt:1308,1357` — live-path Nyquist (defensible, capture is 44.1k, but still magic).
- `MainScreen.kt:418` — `sampleRate = 44100` passed to `SpectrogramCanvas` in **all** modes, so the frequency axis is mislabeled for a 48 kHz file (a real 4,000 Hz tone displays as ≈3,674 Hz).
- `TelemetryGraph.kt:38` — `sampleRate: Int = 44100` default, never overridden by the caller.
- `MainViewModel.kt:95` — playback biquad filters built with `44100.0`, shifting every cutoff by fs/44100.
- `PdfReportGenerator.kt:82,201` — PDF axes and duration hard-code 44100 and hop 1024.
- `SettingsDialog.kt:50` — the "expert DSP table" (Δf, Δt, fps) hard-codes 44100.
- `MainViewModel.kt:1047` — `historySize` computation.

**Impact:** for the extremely common case of analyzing a phone video (48 kHz audio), every displayed frequency, every order projection (H1 overlay, tracked-order dBFS), every report frequency range, and every PDF axis is wrong by 8.8 %. This is silent — the app renders confidently wrong numbers. For a measurement tool this is the single worst defect in the codebase.
**Fix:** thread `sampleRate` from `LoadedWavData` (or the capture config) through `FFTProcessor`, all canvases, the order tracker, and the report generators. Delete every literal `44100` outside a single constants declaration for the live-capture configuration.

### C2. WAV parsing is wrong for non-canonical, stereo, and non-16-bit files — **Critical**
`WavDataReader.parseWavStream` (`WavDataReader.kt:45–85`):
- Assumes the `data` chunk starts at byte 44. WAV files with `LIST`/`fact`/`bext`/extensible-fmt chunks (very common from DAWs and recorders) will have metadata bytes decoded as audio samples.
- Validates only two magic bytes (`header[0] == 'R'`, `header[8] == 'W'`).
- Reads `channels` (line 61) and `bitsPerSample` (line 62) and then **ignores both**: stereo files are treated as mono (interleaved L/R decoded as consecutive samples → spectral garbage and duration wrong by 2×, line 85), and 24-bit/32-bit-float files are decoded as 16-bit PCM noise.
- Allocates `maxDurationSec * bytesPerSec` up front (line 69): 52.9 MB for a CD-format file even if the file is 10 seconds long; ~259 MB for a 96 kHz/24-bit stereo header → OOM. The known `fileLen` parameter is never used to size the buffer.

**Impact:** "Import external WAV" (`wavPickerLauncher`, any file via SAF) produces silently corrupt analyses for a large share of real-world files.
**Fix:** proper RIFF chunk walking (find `fmt `/`data`), reject or convert unsupported formats with a user-visible error, honor channel count (downmix), size buffers from the actual data-chunk length.

### C3. Files longer than 5 minutes: playback position and spectrogram silently desynchronize — **Critical**
The PCM is capped at 5 minutes (`WavDataReader.kt:64`, `VideoAudioExtractor.kt:53`) but the loaded duration is then overwritten with the *full media duration* from `MediaPlayer` (`MainViewModel.kt:337,362,412`) — and `VideoAudioExtractor.kt:115` likewise returns the full container duration. `processWavFrameAt` (`MainViewModel.kt:834`) maps `positionMs / durationMs` linearly onto the truncated frame list. For a 10-minute video, the playhead at 8:00 shows the spectrum from 4:00.
**Impact:** every displayed spectrum, telemetry interpolation, tag lookup, and the amber playhead is wrong for long files, without any warning ("limité à 5 min max" appears only in helper text).
**Fix:** clamp `durationMs` to the analyzed PCM duration (or refuse/segment long files explicitly).

### C4. Recording save path: main-thread I/O with a crash/data-loss path on Android 10 — **Critical**
`saveAudioRecording` (`MainViewModel.kt:977–1024`) runs **synchronously on the main thread** (no coroutine): assembles the full PCM, writes the WAV, builds JSON by string concatenation, writes it. A 30 s recording is ~2.6 MB plus directory creation — ANR territory, and any `IOException` from `WavAudioWriter`/`writeText` is uncaught → crash. It writes via `Environment.getExternalStoragePublicDirectory` (deprecated since API 29; on Android 10 without `requestLegacyExternalStorage` the `mkdirs`/write fails) — the user's measurement is then lost with no feedback. `WavSelectionDialog.kt:32–54` does the matching directory listing on the main thread during composition.
**Fix:** MediaStore (`MediaStore.Downloads`) or SAF, on `Dispatchers.IO`, with success/error surfaced to the UI.

### C5. Every audio-settings change permanently leaks a competing frame consumer — **High**
`startRecording()` (`MainViewModel.kt:1134`) launches three coroutines: a telemetry collector (`:1138`, flow never completes), an audio producer, and a channel consumer (`for (frame in audioBufferChannel)`, `:1171`). None of these jobs is stored or cancelled. `stopRecording()` (`:1478`) only stops the `AudioRecord`. Changing FFT size calls `stopRecording(); startRecording()` (`:1079–1082`), so after N settings changes there are **N+1 live consumers** competing for the same channel and **N+1 telemetry collectors** double-writing `_telemetryState` and `gpsHistory`. Because a channel delivers each frame to exactly one consumer, per-bin persistence counters (`ttnrPersistenceCount`), the retro-unmask buffer, and the EMA each see only a fraction of the frames — the 6-consecutive-frames TTNR validation logic silently breaks. Additionally, the producer coroutine never finishes: after the read loop exits, `callbackFlow` parks forever in `awaitClose` (`AudioRepository.kt:65`) because nothing cancels the collector.
**Fix:** hold `Job` references, cancel on stop; or model capture as a single `flatMapLatest` pipeline keyed by settings.

### C6. All live DSP runs on the main thread — **High**
The consumer at `MainViewModel.kt:1170` is `viewModelScope.launch { … }` — `Dispatchers.Main`. Per frame (~43 Hz): 2048-point complex FFT, TTNR computation, two full-history list copies (`:1272–1296`), retro-unmask row cloning, a 1,000-bin order sweep with tag/report bookkeeping (`:1361–1470`) — all on the UI thread that is simultaneously recomposing the entire screen. `recalculateOrderTrackingForWav` (`:445–631`) also runs on Main — for a 5-minute file that is ~13,000 frames × 1,000-bin order mapping on the UI thread (visible freeze after every kinematics change). `exportData` (`:1483`) builds and compresses a 1400×1850 bitmap plus a per-pixel spectrogram loop on Main.
**Fix:** move the consumer and all sweeps to `Dispatchers.Default`, exports to `Default`+`IO`; keep only `StateFlow` writes on Main.

### C7. The microphone stays hot for the entire app lifetime — **High** (privacy + battery + correctness)
Capture starts in `init` (`MainViewModel.kt:1130`) and is never stopped when switching to WAV/Video mode — `setAudioSourceMode` (`:264`) cancels processing but not capture; the consumer merely discards frames when not LIVE (`:1203`). There is no UI to stop it either: `toggleRecording()` (`:1111`) and the collected `isRecording` state have **no callers in any screen** — dead controls. GNSS full-tracking (`TelemetryRepository.kt:95–105`, duty-cycling disabled deliberately) plus 200 ms location updates run for the entire session too. On Android 12+, the mic-in-use indicator will show permanently — for a professional tool this looks like spyware behavior and drains battery.
**Fix:** stop capture (and optionally location) when leaving LIVE mode and when backgrounded; release in `onCleared()`.

### C8. `MIC` audio source undermines measurement stability — **High** (for a measurement app)
`AudioRepository.kt:38` uses `MediaRecorder.AudioSource.MIC`, which on most devices applies automatic gain control, noise suppression, and EQ tuned for voice. Absolute dBFS values and tone-to-noise ratios are therefore device-processed and time-varying. Android provides `UNPROCESSED` (API 24 — exactly this app's minSdk) with a support property check, and `VOICE_RECOGNITION` as fallback — the standard choice for measurement apps.
**Fix:** prefer `UNPROCESSED` when `PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED` is set; document the fallback in the report metadata.

### C9. `AudioRecord` used without state validation → crash risk — **High**
`AudioRepository.kt:37–45`: the `AudioRecord` is constructed and `startRecording()` called without checking `state == STATE_INITIALIZED`. If the mic is busy (phone call, another recorder) or init fails, `startRecording()` throws `IllegalStateException` inside `callbackFlow` → uncaught in `viewModelScope` → **process crash**. Also: on a short read, `System.arraycopy(readBuffer, 0, slidingWindow, fftSize - stepSize, readResult)` (`:58`) leaves stale samples in the tail of the window; and a persistent read error (negative return) spins the loop hot without backoff.

### C10. Audio filters change what you hear but not what you see — **High** (misleading)
`addAudioFilter`/`removeAudioFilter` (`MainViewModel.kt:58–67`) rebuild the *playback* file through the biquads, then call `processFullWavSpectrogram(originalData)` — which performs FFT on the **unfiltered** PCM (`:648–687`; `_activeFilters` is never consulted there). The spectrogram recompute is therefore a no-op that burns seconds of CPU to redraw the identical image, while the analyst hears filtered audio against an unfiltered display. The filter overlay bands drawn on the canvas are the only visual hint. Either apply the filters to the analyzed PCM as well (recommended — that is what "FILTRES AUDIO DSP (QUALITÉ AAA)" implies), or don't reprocess and label the feature as playback-only.

### C11. Silent, locale-sensitive parsing of kinematic parameters — **High** (French-market app!)
`KinematicsDialog.kt:57–68`: every numeric field uses `toDoubleOrNull() ?: <default>`. A French user typing `9,5` (comma decimal — the national convention, and what many soft keyboards produce in `KeyboardType.Number`) gets `null` → the value silently reverts to the default (e.g., V1000 = 10.0) with **no error indication**, corrupting every RPM/H1/order computation downstream. `OrderSelectionDialog.kt:112` handles the comma correctly — the inconsistency proves the hazard is real. Also `KeyboardType.Number` should be `Decimal`.
**Fix:** normalize `,`→`.` before parsing everywhere, show field-level validation errors, never silently substitute defaults.

### C12. Video extraction drops the decoder's tail and boxes every sample — **Medium**
`VideoAudioExtractor.kt:56` — the outer loop exits as soon as the input side queues EOS (`isEOS` set at `:64`), before draining remaining output buffers: the final fraction of a second of audio is silently lost. PCM accumulates in `ArrayList<Short>` (`:48`) — 13.2 M boxed objects for 5 min at 44.1 kHz (~250 MB of object overhead) → GC storms and OOM risk on mid-range devices. `INFO_OUTPUT_FORMAT_CHANGED` is not handled, so the actual decoder output rate/channel count is assumed, not verified. During extraction there is no progress state at all (`_isProcessingVideo` is only set later in `processFullWavSpectrogram`), so the UI sits idle for the many seconds a 5-minute video takes to decode.

### C13. Settings changes in WAV mode wipe the analysis — **Medium**
`updateSettings` (`MainViewModel.kt:1073–1083`) on FFT-size change clears `_fftHistoryAbsolute/TTNR` and `_telemetryHistory` unconditionally and restarts *live* capture — but in WAV/Video mode nothing re-triggers `processFullWavSpectrogram`, leaving a blank spectrogram, stale `wavTagsByFrame`, and a dead display until the file is manually reloaded. (The FFT-size radio buttons are hidden in WAV mode, but the code path remains reachable via the shared dialog callbacks, e.g. Min/Max dB is fine but the guard is by-UI-convention only.)

### C14. Display range can be inverted with no guard — **Medium**
`SettingsDialog.kt:162–174`: `minDb` slides up to 0 and `maxDb` down to −40 with no cross-constraint, so `minDb > maxDb` is reachable. Normalization `(v−min)/(max−min)` then inverts/exceeds [0,1] (clamped to garbage colors) across the canvas, exports, and PDF. Clamp `min < max − ε` at the ViewModel boundary.

### C15. ProGuard keep rule targets a nonexistent package — **Medium**
`proguard-rules.pro`: `-keep class com.github.wendykierp.jtransforms.** { *; }` — JTransforms classes actually live in `org.jtransforms.**` (see the import in `FFTProcessor.kt:3`). The rule as written keeps nothing; release builds rely on R8 reachability alone, and any reflective path inside JTransforms/JLargeArrays (`ConcurrencyUtils` thread config) is unprotected. Given release uses `proguard-android-optimize.txt` with minify+shrink, this is a genuine release-only breakage risk that unit tests (which don't exist) would never catch. The `-keepclassmembers @Composable` rule is meanwhile pointless bloat.

### C16. WAV loading parses the entire file on the main thread — **High**
`loadWavFile` and `loadWavFromUri` (`MainViewModel.kt:323–371`) call `WavDataReader.readWavFile/readWavFromUri` **synchronously**, directly from Compose click callbacks (`MainScreen.kt:121`, `MainScreen.kt:1008`). That is a full-file read plus the up-front `maxBytesToRead` allocation (52.9 MB for CD format, see C2) plus JSON telemetry parsing — all on the UI thread. A 5-minute file freezes the app for the whole read (ANR risk); only the *FFT* stage afterwards is dispatched to `Dispatchers.Default`. The video path does this correctly (`loadVideoFromUri` wraps extraction in `launch(Dispatchers.Default)`, `:407`) — the WAV path simply never got the same treatment.
**Fix:** move load+parse into the same background pipeline as the FFT pass, with a loading state the UI already knows how to show (`_isProcessingVideo`).

### C17. Manual-order speed/RPM ranges are computed from the wrong telemetry samples in WAV mode — **High**
`validateCurrentOrder` (`MainViewModel.kt:1920–1946`) iterates path anchors whose `frameIndex` is an **FFT-frame index** (0…~12,900 for a 5-minute file) and uses it directly as a **telemetry-list index**: `if (f in telemHistory.indices) { val telem = telemHistory[f] … }`. In live mode the two lists happen to be appended 1:1, so this works. In WAV-analyzer mode `_telemetryHistory` holds the raw imported telemetry (e.g., ~30 entries for a 30 s recording) — so only anchors with `frameIndex < 30` contribute at all, and `telemHistory[7]` is the sample at ≈7 s while frame 7 is at ≈0.16 s. The min/max speed and RPM printed next to each validated order — on screen (`ReportModeScreen` table) and in the **customer PDF** — are therefore drawn from the wrong instants or missing entirely for WAV analyses. The correct ratio-mapping code already exists 1,000 lines earlier in `processWavFrameAt` (`:857–875`); this function never adopted it.
**Fix:** map `frameIndex → time ratio → telemetry index` exactly as `processWavFrameAt` does.

## 3. DSP & Measurement Integrity Assessment

**What is right (credit where due):**
- Hann amplitude calibration `mag/(N/4)` (`FFTProcessor.kt:37`) is the correct normalization for a full-scale on-bin sine with a Hann window under a complex FFT — 0 dBFS reads as 0 dBFS.
- 50 % overlap sliding-window capture (`AudioRepository.kt:47–62`) is the correct STFT structure.
- Sub-bin parabolic peak interpolation with ±0.5 bin clamp (`MainViewModel.kt:1853–1863`) is textbook-correct.
- The kinematics math (`KinematicsData.kt`) — tire radius from sidewall geometry with 1.5 % load deflection, V1000 equivalence across three input modes — is clean, testable, and dimensionally correct.

**Where it falls short of a measurement-grade bar:**

- **D1 (High).** `computeTTNR` claims "ECMA-74 / ISO 1996-2" compliance (`FFTProcessor.kt:58`) but is an ad-hoc heuristic. The core unit error: bins are *amplitude*-calibrated (coherent gain, `mag/(N/4)`), but the noise estimate treats bin-power sums as a PSD (`pNoiseSum/(noiseCount·df)`, `:146`) with **no ENBW correction** — for a Hann window every noise bin carries 1.5 bins' worth of power (ENBW = 1.5, i.e. +1.76 dB), while the tone side is summed over ±2 bins of coherently-calibrated leakage. Tone and noise are therefore calibrated in *different* unit systems, giving the ratio a fixed bias of roughly 1.8 dB that nothing compensates. On top of that: Terhardt critical bandwidth arbitrarily clamped to [150, 350] Hz, a constant `minEmergenceRequired = -3.0` labeled "adaptatif en fréquence" (`:165`), and a hybrid `max()` of two different metrics (`:169`). As an internal detection score this is fine; **printing it on customer-facing PDF reports under a standards name is a professional-liability issue.** Either implement the standard or rename the metric honestly (e.g., "NVH emergence index").
- **D2 (High).** Sentinel values are fed into arithmetic. `-100.0` "no tone" markers enter the temporal EMA (`FFTProcessor.kt:214`, `MainViewModel.kt:1263`): a real 20 dB tone that drops out one frame blends to 0.75·(−100)+0.25·20 — the "smoothing" actually produces instant cut-offs and one-frame onset delays rather than the documented 110/220 ms integration. Comments contradict each other (τ=220 ms at `:59`, τ=110 ms at `:204`) and both contradict the math: at the 43.07 fps frame rate (hop 1024 / 44.1 kHz = 23.2 ms), α = 0.36 gives τ = −Δt/ln(1−α) ≈ **52 ms** — neither documented value. A related unit mix: the 150 ms retroactive unmask writes *raw* TTNR values back into rows of the *EMA-smoothed* history (`MainViewModel.kt:1282–1293`), so unmasked columns sit on a different scale than their neighbors. Use linear-power EMA with a floor, or track "presence" separately from level.
- **D3 (Medium).** The transient-shock detector (`FFTProcessor.kt:78–84`) compares consecutive *calls*, not consecutive *times* — its sensitivity silently depends on frame rate, and the shared `lastFrameEnergyDb`/`integratedTtnr` state makes `FFTProcessor` stateful and single-stream-only (correctly worked around by creating a local instance for WAV sweeps, `MainViewModel.kt:665` — but the constraint is undocumented and fragile). A telling detail: `lastFrameEnergyDb` initializes to −120 (`:9`), so the very first frame of every stream is always ≥6 dB above it and is **always squelched as a "shock"** — the analysis provably starts with a discarded frame, and no test exists to notice.
- **D4 (Medium).** The "8th-order Butterworth" cascade (`MainViewModel.kt:90–97`) is only Butterworth for LOW/HIGH-pass: for BAND_PASS/BAND_STOP the `q` parameter is ignored by `BiQuadFilter` (bandwidth-octave formula used instead, `BiQuadFilter.kt:66–100`), so the cascade is four *identical* sections — the −3 dB points become −12 dB points and the shape is not Butterworth. The comment overpromises.
- **D5 (Medium).** `BiQuadFilter.process()` (`BiQuadFilter.kt:116–126`) is an abandoned, *incorrect* implementation (uses `z1/z2` as both input and output state) left in the class alongside its stream-of-consciousness comments: *"Wait, the above is Direct Form II transposed or Direct Form II? … let's use standard Direct Form I just to be safe."* It is unused (`processSample` is the real one) — but unreviewed generated code with visible doubt-monologue committed to production is exactly what an AAA process must catch. Delete it.
- **D6 (Medium).** `processFFT` allocates a `2*fftSize` double array + magnitudes array per call at 43 Hz (`FFTProcessor.kt:24,36`) and uses `complexForward` with zero imaginary parts where `DoubleFFT_1D.realForward` would halve the work and memory. Preallocate and reuse.
- **D7 (Low).** Frequency-domain masking of everything below 30 Hz inside the FFT (`FFTProcessor.kt:42–44`) conflates display policy with computation; the 43/45 Hz gates in TTNR add more magic constants. Whitelist tolerance is 0.25 orders in one place (`MainViewModel.kt:1399`) and 0.2 in the merge (`:1424`); live search radius is ±1 bin (`:1316`) vs ±3 in the WAV sweep (`:471`). None of these constants is named, sourced, or shared.
- **D8 (Low).** Jet colormap (`SpectrogramColormap.kt:49`) is perceptually non-uniform and creates false luminance edges — the scientific-visualization consensus is Viridis/Turbo for quantitative reading. Defensible as a legacy-NVH convention, but an AAA measurement tool should at least offer a perceptually uniform option.
- **D9 (Low).** No scalloping correction. A Hann-windowed bin readout underestimates a tone that falls between bins by up to **1.42 dB** (worst case at bin+0.5). The tracked-order dBFS curve (`trackedOrderDbFS`, plotted in the 2D order graph and stored in reports) takes the max over a ±1-bin window without interpolating amplitude, so as an order sweeps in frequency the reported level ripples by ~1.4 dB purely from bin alignment — visible as periodic dips in the order trace that have nothing to do with the vehicle. The parabolic interpolator that already exists for *frequency* refinement (`MainViewModel.kt:1853`) could correct *amplitude* for free.

### 3b. GPS speed acquisition — deep dive

Speed is not telemetry garnish in this app: it is the *reference input of the measurement chain*. Every H1 projection, order tag, whitelist match, and RPM printed on a report derives from it via `f(H_k) = k · v · (1000/V1000)/60`. The error budget follows directly: with V1000 = 10 km/h, **H18 moves 30 Hz per km/h of speed error**, against a live search window of ±1 bin = ±21.5 Hz (`MainViewModel.kt:1316`). So the tracker tolerates roughly **±0.7 km/h** of speed error at H18 before it locks onto the wrong bin — speed acquisition quality directly bounds the highest order the app can track.

**Verdict on the core choice: correct.** `Location.getSpeed()` on a GNSS fix is Doppler-derived by the chipset — accurate to ~0.1 m/s (≈0.36 km/h ⇒ ~11 Hz at H18, inside one bin). This is *far* better than differentiating positions (1–3 km/h error under multipath ⇒ 30–90 Hz at H18 — tracking would break), and better than any phone-sensor alternative. Using Doppler speed as the primary signal is the right call, and the deliberate "100% GPS" acceleration (no accelerometer mounting-angle problems) is a defensible field decision. **The access method around that signal, however, has five concrete defects:**

- **G1 (Medium). Wrong clocks: `loc.time` deltas and cross-clock matching.** Acceleration is differentiated over `loc.time` deltas (`TelemetryRepository.kt:54,61–68`) — a UTC wall-clock that can step (NTP corrections, GNSS week adjustments, user changes); Android's own guidance is to use `Location.getElapsedRealtimeNanos()` (monotonic) for any interval math. A clock step of 1 s at 1 Hz fixes doubles or zeroes `dt` → **acceleration spikes of ±100 % that look like real vehicle events**. Worse, the GMPe live path *brackets across two different clocks*: `AudioFrame.timestampMs` is `System.currentTimeMillis()` (`MainViewModel.kt:1165`) while `TelemetryData.timestampMs` is `loc.time` (`TelemetryRepository.kt:86`) — and the 5 s history cutoff mixes them again (`MainViewModel.kt:1156`). The entire 1.2 s interpolation design (L5) silently assumes the device clock and GPS time agree to well under 1.2 s; on a device with a few seconds of clock skew (common without network sync), the `before/after` bracket at `:1188–1189` finds no `after` sample and interpolation silently degrades to nearest-past — no error, just a stale theoretical speed. One default even mixes a third source: `TelemetryData()` instances stamp `System.currentTimeMillis()` (`TelemetryRepository.kt:31`).
- **G2 (Medium). Fused provider without provenance, at a fantasy rate.** `FusedLocationProviderClient` with `PRIORITY_HIGH_ACCURACY` at 200 ms/100 ms intervals (`TelemetryRepository.kt:47–49`) can deliver positions fused from GNSS, Wi-Fi, cell, and sensors; nothing filters fixes by provenance, and a network-derived fix carries no (or garbage) speed — the code then silently substitutes `0f` (`:55`), which the kinematics gate reads as "vehicle stopped" and drops all order tracking. The requested 5–10 Hz is also fiction: phone GNSS hardware delivers ~1 Hz fixes; the comment "Fréquence d'échantillonnage élevée" documents an intention the hardware ignores. The callback also reads only `result.lastLocation`, discarding any batched intermediates. For a metrology app the deterministic choice is `LocationManager.requestLocationUpdates(GPS_PROVIDER, …)` — the `LocationManager` instance *already exists* in the class (`:38`, used only for the GNSS-tracking hack) — or at minimum filtering fused results to GNSS-sourced fixes with `hasSpeed()`.
- **G3 (Medium). The relevant accuracy API is ignored; the LED grades the wrong quantity.** Since API 26 (`minSdk` is 24, so one version guard), `Location.hasSpeedAccuracy()` / `getSpeedAccuracyMetersPerSecond()` report the 1-σ error of the *exact quantity this app lives on*. The app never reads it. Instead `GpsStatus` is graded from *horizontal position* accuracy (10 m/30 m thresholds, `:73–77`) — a proxy that can be green while Doppler speed is degraded (urban canyon: position holds via fusion, Doppler multipath corrupts speed) and red while speed is fine. The status LED that tells the operator "trust these RPM numbers" is keyed to the wrong error term, and speed samples are used identically whether the fix is GOOD or NONE — quality gates nothing.
- **G4 (Low). No estimator: raw samples straight into the pipeline.** Speed is used unfiltered — no outlier rejection, no hold-last-known on dropout (silent `0f`, see G2), no smoothing — and acceleration is a raw first difference of a 1 Hz signal. A minimal constant-acceleration estimator (α-β or 1-D Kalman over Doppler speed, ~30 lines) would: reject single-fix outliers, bridge 1–2 s dropouts gracefully, output acceleration as a by-product (replacing the spiky derivative of G1), and — the architectural payoff — **predict speed forward, eliminating the 1.2 s display latency** (L5) that exists solely because linear interpolation needs a *future* fix. The delay-and-interpolate design is a defensible accuracy-over-latency trade, but it is undisclosed to the user and unnecessary once a predictor exists.
- **G5 (Low). Full-tracking GNSS registered for its side effect only.** The `GnssMeasurementsEvent` callback with `setFullTracking(true)` (`TelemetryRepository.kt:95–105`) is *empty* — raw measurements are requested at full duty cycle purely to keep the receiver from power-saving between fixes. It burns battery for data that is discarded, silently does nothing below API 31 or without permission (`catch {}`), and duplicates what a high-priority active `LocationRequest` largely achieves anyway. If raw measurements are worth their power cost, use them (carrier-phase-smoothed Doppler is the metrology-grade upgrade path); if not, drop the registration.

**Recommended target design** (ordered, mostly independent): (1) subscribe GNSS-only (or filter fused fixes to GNSS provenance), keep fused as fallback; (2) switch every interval and history-matching computation to `elapsedRealtimeNanos`; (3) gate on and display `speedAccuracyMetersPerSecond`, falling back to horizontal accuracy pre-API 26; (4) add the small speed estimator and delete both the raw-difference acceleration and the 1.2 s delay; (5) longer-term, an optional OBD-II/CAN wheel-speed source would make order tracking immune to tunnels and urban canyons — the only regime where even correct GNSS Doppler fails.

## 5. Concurrency & Lifecycle (beyond C5–C7)

- **L1 (High). No `onCleared()`.** `MediaPlayer` is never released on ViewModel destruction; the `Channel` is never closed; `AudioRepository` relies on scope cancellation reaching the flow (it does) but the player and any pending temp state do not.
- **L2 (Medium). Filter-rebuild races.** `applyDigitalFiltersToPlayback` (`MainViewModel.kt:85–120`) launches an unmanaged job per toggle; rapid changes race on the same `filtered_playback.wav` cache file and on `initMediaPlayer`, and the playback position is captured *after* the multi-second filtering completes rather than before.
- **L3 (Medium). Unprotected shared mutable state.** `emaOrderSpectrum`, `ttnrPersistenceCount`, `recentRawTTNRBuffer`, `previousTTNRSpectrum`, `wavTagsByFrame` are plain fields touched from multiple coroutines; today everything happens to run on Main (see C6) so there are no memory races — fixing C6 without introducing a confinement strategy will create them. The design gives no hint of this coupling.
- **L4 (Medium).** `initMediaPlayer` calls synchronous `prepare()` on the main thread (`MainViewModel.kt:312`) — for content URIs (video mode) this can block for hundreds of ms; `prepareAsync` exists for exactly this.
- **L5 (Low). GMPe live latency by design.** The consumer deliberately delays every frame to 1.2 s of age (`MainViewModel.kt:1176–1182`) so GPS interpolation brackets the timestamp. Clever, but: the spectrogram silently lags reality by 1.2 s in GMPe live mode (nowhere disclosed to the user), the backlog (~52 frames in the UNLIMITED channel, `:1127`) drains as a visual burst when kinematics is toggled off, and if per-frame processing ever exceeds ~23 ms the unbounded channel grows without limit.
- **L6 (Low).** `stopWavPlayback` nulls the player, but `startWavPlayback` silently no-ops afterwards until a reload re-inits — mode switches rely on call-order luck rather than a state machine.
- **L7 (Medium). Analysis state is never reset across mode transitions — ghost data.** `setAudioSourceMode` (`MainViewModel.kt:264–279`) clears histories and loaded media, but **not** the analysis-engine state: `emaOrderSpectrum` (`:129` — its only writes are the blend at `:1379`; no reset call exists anywhere), `previousTTNRSpectrum` (`:1119`), `_latestTTNRSpectrum`, and `ttnrPersistenceCount` (cleared only via `clearEmergenceReport`, which mode switching never calls). Concrete symptom: run live with GMPe on a vehicle, switch to WAV mode and back — the order-domain EMA still holds the previous session's excitation, so tags for orders that are no longer present can re-fire immediately at `>2 dB` threshold (`:1383`) until the stale EMA decays (~10 s at α=0.10/43 fps). Same story after changing the kinematic config (a different V1000 remaps every order index, but the EMA built under the old mapping persists). A `MeasurementSession` object with an explicit `reset()` on any source/config change would eliminate the class of bug.

  Per-transition stale-state summary:

  | Transition | Cleared | Left stale |
  |---|---|---|
  | LIVE → WAV/VIDEO | histories, telemetry, media | mic capture (still hot, C7), `emaOrderSpectrum`, `previousTTNRSpectrum`, persistence counters, `_latestTTNRSpectrum` |
  | WAV/VIDEO → LIVE | histories, loaded media | `wavTagsByFrame` (map retained; only unused because mode-gated at `:912`), EMA/persistence state seeded by the WAV sweep's live-instance leftovers |
  | Kinematics config change (live) | nothing | entire order-domain EMA built under the previous V1000 mapping |
  | FFT-size change | histories (even in WAV mode — C13) | one **extra** channel consumer + telemetry collector (C5), stale `wavTagsByFrame` |

## 6. Performance & Memory

- **P1 (High). Unbounded in-RAM analysis.** A full analysis holds: entire PCM (`ShortArray`, up to 26.5 M samples), `absList` + `ttnrList` of ~12,900 frames × 1,024 doubles × 8 B × 2 ≈ **211 MB** for a 5-minute 44.1k file (`MainViewModel.kt:667–687`) — before the UI builds a `12,900 × ≤1,023` bitmap (`SpectrogramColormap.kt:161–166`): a ~52 MB `IntArray` **plus** a ~52 MB `Bitmap`, filled pixel-by-pixel **on the main thread** in a `LaunchedEffect` (`:171–225`) — seconds of frozen UI, repeated on every display-mode or dB-range change. Downsample frames to display resolution (the canvas is ~1,000 px wide; 13k columns are wasted), store spectra as `FloatArray`, and render off the UI thread.
- **P2 (Medium). Per-frame allocation churn at 43 Hz (live).** Two full history-list copies + two 8 KB `DoubleArray`s + a cloned TTNR row + tag list rebuilds per frame (`MainViewModel.kt:1232–1296`), plus `values = history.map{…}` boxing ~1,300 doubles per draw in `TelemetryGraph.kt:273`, plus `Paint()` objects constructed inside the draw loop (`SpectrogramColormap.kt:547–556, 727–738, 936–950`; `816` allocates a Paint *per label per frame*). Use ring buffers and hoisted paints.
- **P3 (Medium). Whole-tree recomposition at frame rate.** `AppScreen` collects ~35 `StateFlow`s at the top (`MainScreen.kt:67–114`); `fftHistory`/`telemetryState` update at ~43 Hz, recomposing the entire scaffold including bottom bar and dialogs. Scope collections to the composables that consume them; use `derivedStateOf` for derived booleans.
- **P4 (Low).** `collectAsState()` everywhere instead of `collectAsStateWithLifecycle()` — the dependency is already declared (`build.gradle.kts:66`) and even used in the dead template file. Flows (and the 43 Hz pipeline) keep running while the app is backgrounded.
- **P5 (Low).** JTransforms 3.1 (2015) drags in commons-math3/JLargeArrays for one `DoubleFFT_1D`; `complexForward` instead of `realForward` doubles the work (see D6). A 60-line radix-2 real FFT or a maintained KMP DSP lib would shrink the APK by megabytes.

## 7. Compose / UI Quality

- **U1 (High). Permission dead-end.** `AppNavigation` (`MainScreen.kt:36–61`) requests all three permissions once in `LaunchedEffect(Unit)`; `permissionsGranted = permissions.values.all { it }`. Deny *location* (extremely common — the user just wants a spectrogram) and the app parks forever on "En attente des permissions…" with no retry button, no rationale, no degraded audio-only mode, no settings deep-link. Restart-and-hope is the only recovery. An AAA app degrades gracefully per-permission.
- **U2 (High). Side effects and time reads in composition.** `MainScreen.kt:806–813` throttles a KPI by reading `System.currentTimeMillis()` and *assigning `remember`ed vars during composition* — non-idempotent recomposition logic that only works because something else recomposes at 43 Hz. `SpectrogramCanvas` mutates a remembered `Bitmap`/`IntArray` in a `LaunchedEffect` and relies on the next recomposition to repaint (`SpectrogramColormap.kt:161–227`) — a one-frame-lag hack; a mode switch leaves *stale columns from the previous mode* on screen until they scroll off (live path repaints only the newest column, `:198–221`).
- **U3 (High). Raw pixels instead of dp/sp.** Plot margins `150f/60f/120f/40f` and text sizes `32f/26f/22f` are physical pixels, duplicated across two `pointerInput` blocks and the draw pass (`SpectrogramColormap.kt:379–385, 416–421, 474–477`; same pattern in `TelemetryGraph.kt:116–119`). On an xxxhdpi phone the axis gutter is ~34 dp with ~9 dp text; on mdpi it's enormous. This is very plausibly the "layout bugs found on device" class of issue. Convert once with `Density`, define margins in one place.
- **U4 (Medium). Zoom/pan misalignment in WAV mode.** Pinch-zoom is active outside report mode (`SpectrogramColormap.kt:412–447`) and the bitmap crops accordingly, but the amber playhead (`:499–512`), emergence beacons (`:626–650`), harmonic tags (`:961–965`), and H1 overlay (`:885–931`) are all positioned in *unzoomed* plot coordinates → overlays detach from the spectrogram as soon as the user zooms. Zoom is only reset when leaving report mode (`:124–129`).
- **U5 (Medium). Theming is incoherent.** The template purple `NVHSpectroTheme` with `dynamicColor = true` (`Theme.kt:36–47`) means brand colors come from the user's wallpaper on Android 12+; the app is designed dark (black canvas, hard-coded white text like `MainScreen.kt:799`) but follows system light theme for surfaces — in light mode, white text lands on light `surfaceVariant` cards. `themes.xml` uses `Theme.Material.Light` (white launch flash into a dark app). Pick one: a fixed dark professional theme, or do the M3 work properly.
- **U6 (Medium). Feature promises the UI can't keep.** "Vidéo YouTube" mode (`VideoPlayerView.kt:156–169`) loads an embed in a JS-enabled WebView but extracts **no audio** — the spectrogram stays empty; it is a video player masquerading as an analysis source (and `parseYouTubeEmbedUrl`'s `else -> url` branch injects arbitrary user input into the embed URL). Local video sync: the `update` lambda only re-seeks on play/pause *transitions* (`:145–152`), so seeking while playing lets the muted `VideoView` drift from the analyzed audio.
- **U7 (Low).** `ReportModeScreen` shows raw `v1000Kmh` (`:209`) while GEAR_RATIO/DETAILED_CHAIN modes are active — displays a value the calculation ignores (main screen correctly uses `getEffectiveV1000()`). PDF path colors use golden-angle HSV (`PdfReportGenerator.kt:232`) while the screen uses a fixed 7-color palette (`MainViewModel.kt:1954`) — the same order has different colors on screen and in the report, and the PDF has no legend linking them beyond list position. The PDF also lacks a date/time and app-version stamp — for a deliverable engineering report, that is a completeness failure.
- **U8 (Low).** Deprecated `Divider` (multiple), `screenOrientation="portrait"` is ignored on large screens at targetSdk 36 (Android 16 large-screen orientation policy) — the layout has no landscape/tablet handling despite being un-lockable there; `android:windowSoftInputMode` sits on `<application>` (`AndroidManifest.xml:14`) where it is not a documented attribute (belongs on the activity); splash is a fixed 2 s vanity delay (`SplashScreen.kt:23`) instead of the Android 12 SplashScreen API.
- **U9 (Medium). Report mode entered from live view shows a time-mirrored spectrogram.** Live history lists are built newest-first (`curAbs.add(0, magnitudes)`, `MainViewModel.kt:1273`), and `toggleReportMode` snapshots them as-is (`:1698–1700`). The report-mode canvas branch maps `x=0 → frame 0` (`SpectrogramColormap.kt:176`) — i.e., the **newest** frame lands at the **left** edge — while the report-mode time axis labels ascend 0 s → total left-to-right (`:1026–1027`), which asserts the opposite. The image the analyst just watched scroll by is silently displayed mirrored relative to its own axis, and manual track anchors inherit the same reversed frame-index space (internally consistent, so drawing works — but C17 then reads telemetry against it). WAV-mode snapshots are chronological, which is why the bug only bites the live→report path ("Rapport Manuel" is enabled in live mode, `MainScreen.kt:206`).
- **U10 (Medium). Frozen-view PNG export is mirrored and mis-scaled in WAV mode.** `exportData` unconditionally reverses columns (`pixels[y*w + (w−1−x)]`, `MainViewModel.kt:1509`) — correct only for the newest-first live history; for a chronological WAV history the exported spectrogram is **time-mirrored**. The stacked telemetry graphs below it map x using the *live* `historySize` (`:1648`) and label the time axis with the *live* `_timeWindowSec` (`:1609,1675`) regardless of the actual WAV duration — so in WAV mode the curves are compressed into a fraction of the plot at the wrong end, under an axis that describes a different timespan. The export path was written for live mode and never audited when the Freeze/Export button became reachable from the analyzer.

## 15. Closing Assessment

The distance between this codebase and its own ambition ("Qualité AAA" appears verbatim in the source at `SettingsDialog.kt:260` and `SpectrogramColormap.kt:550`) is not talent — the DSP thinking is real — it is **process**. Nearly every serious defect in this audit shares one root cause: changes were applied as unreviewed textual patches without tests, without a compiler-guarded refactor loop, and without a second reading. The result is an app that demos brilliantly at 44.1 kHz on the author's phone and quietly betrays its numbers everywhere else.

The single highest-leverage decision available is also the one already taken: the from-scratch v2 rebuild. For as long as V13.1 remains the shipping artifact, the P0 list above is the minimum bar for trusting the numbers it prints on a customer report.
